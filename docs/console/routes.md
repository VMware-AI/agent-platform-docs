# 网关路由

> 模型调度台 → 网关路由 · 需要 <span class="ap-badge admin">admin</span>

管理网关上的路由清单：一条路由 = 一个对外的**逻辑模型名** + 一组底层供应商模型 + 一套分派策略 + 降级链。

::: danger 智能体请求里写的是路由名
这是最容易搞错的一点。agent 发出的 `model: "..."` 必须是**路由名**，不是上游模型原名、也不是[模型管理](/console/models)里的模型名称。写错直接 404「模型不存在」。
:::

## 新建路由

点 **新建路由**：

| 字段 | 约束 | 说明 |
|---|---|---|
| 路由名称 | **大写字母、数字与中划线**，2–64 字符 | 智能体请求里写的模型名 |
| 模型网关 | 必填 | 该路由归属的网关 |
| 路由策略 | 见下表 | 多个后端模型之间怎么分派 |
| 选择路由的模型 | 穿梭框 | 左「可选模型列表」→ 右「已选定的模型」 |

::: tip 命名建议
路由名会直接出现在每个 agent 的配置里，改名成本高。建议一开始就用**稳定的能力名**而不是型号名 —— `CODE-FAST`、`CODE-STRONG`、`CHAT-GENERAL` 比 `QWEN-72B-V2` 更耐用：底层换模型时路由名不用动，所有 agent 无感。
:::

::: warning 穿梭框为空
- 「可选模型列表」为空 → 还没选模型网关
- 提示「该网关暂无可用模型」→ 该网关下还没登记模型，先去[模型管理](/console/models)建
:::

## 路由策略

| 策略 | 行为 | 适用 |
|---|---|---|
| 简单洗牌 `SIMPLE_SHUFFLE` | 随机分流 | 多个同质实例，最省心的默认值 |
| 最闲优先 `LEAST_BUSY` | 选当前并发最少的 | 长请求、并发波动大 |
| 延迟优先 `LATENCY_BASED_ROUTING` | 选历史延迟最低的 | 对响应时间敏感的交互式场景 |
| 使用率优先 `USAGE_BASED_ROUTING_V2` | 按用量均衡 | 多实例配额需要摊平 |
| 成本优先 `COST_BASED_ROUTING` | 选单价最低的 | 成本敏感、质量差异可接受 |

::: tip 成本优先依赖单价
`COST_BASED_ROUTING` 需要每个 spec 都配了输入 / 输出单价才有意义。没配单价时它退化成近似随机。
:::

网关本身也有一个「默认路由策略」（在[模型网关接入](/console/gateway-connections)里配），路由未指定时继承它。

## 降级链

展开「高级参数」可配置三类降级目标。每类都是一个**有序的路由列表**，按顺序顺延。

| 降级类型 | 触发条件 | 典型配置 |
|---|---|---|
| **常规故障转移** | 任何网络错误或限流（含 429、5xx、连接失败） | 主路由 → 备用路由 |
| **上下文超限降级** | 请求超出模型最大 token | 小上下文模型 → 大上下文模型 |
| **内容策略降级** | 触发内容审查拦截 | 严格模型 → 更宽松的模型 |

::: warning 降级目标是「路由」，不是「模型」
下拉里列的是同网关下的**其他路由**。提示「暂无可作为降级目标的路由」说明该网关下只有当前这一条，先把第二条建出来。
:::

::: danger 别配成环
A 降级到 B、B 又降级到 A，故障时会来回打转直到超时。降级链应该是**单向收敛**的：能力从强到弱、成本从高到低，最后一跳是一个最稳的兜底路由。
:::

## 列表与操作

| 列 | 说明 |
|---|---|
| 路由名称 | 智能体调用时使用的模型名 |
| 模型网关 | 归属网关 |
| 路由策略 | 当前策略 |
| 网关模型 | 该路由挂载的模型列表 |
| 创建 / 更新时间 | 排序字段 |

行内操作：**编辑**、**管理**。工具栏：**同步路由**、**刷新**、**批量删除**。

路由还有一个**启用 / 禁用**开关：禁用后该路由不再接收请求，但配置保留 —— 比删除更适合临时下线。

::: tip 什么时候要点「同步路由」
平台改完配置后会自动推送到网关。如果网关侧没立即生效（比如网关刚重启、或同步状态显示「部分同步」），点「同步路由」强制重推一次。
:::

## 一条路由的完整生命周期

<ol class="ap-steps">
<li><strong>准备底层模型。</strong> 建两条模型登记 <code>qwen-72b-bj</code>（北京机房）与 <code>qwen-72b-sh</code>（上海机房），都指向同一个上游模型原名。</li>
<li><strong>建主路由。</strong> 新建 <code>CODE-STRONG</code>，策略选「最闲优先」，把两条模型都挑进已选定列表。</li>
<li><strong>建兜底路由。</strong> 再建一条 <code>CODE-FAST</code>（挂更小更稳的模型）。</li>
<li><strong>配降级链。</strong> 编辑 <code>CODE-STRONG</code> → 高级参数 → 常规故障转移选 <code>CODE-FAST</code>。</li>
<li><strong>收作用域。</strong> 颁发<a href="/console/keys">虚拟密钥</a>时把可调用模型限定为这两条路由。</li>
<li><strong>下发。</strong> 智能体请求 <code>model: "CODE-STRONG"</code>，网关按策略分派；主路由全挂时自动落到 <code>CODE-FAST</code>。</li>
<li><strong>验证。</strong> 到<a href="/observability/request-log">请求日志</a>按模型筛，确认真的有流量落在预期的路由上。</li>
</ol>

## 常见问题

| 现象 | 处理 |
|---|---|
| 智能体报「模型不存在」 | 请求里写的不是路由名；或该密钥作用域不含这条路由 |
| 配了降级链但没生效 | 确认降级目标路由本身健康且已启用；点「同步路由」重推 |
| 路由挂的模型全被熔断 | 调用失败并走降级链；去[模型管理](/console/models)解除熔断 |
| 改了策略但流量分布没变 | 点「同步路由」；部分策略需要积累一段观测数据才生效（如延迟优先） |
| 想临时下线一条路由 | 用启用 / 禁用开关，不要删除 —— 删了配置就没了 |
| 路由名想改 | 改名会让所有引用它的 agent 立刻失效，需同步更新每台 VM。尽量别改 |
