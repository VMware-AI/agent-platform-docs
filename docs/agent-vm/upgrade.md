# 升级与回滚

智能体的版本升级**在 VM 内完成**，不需要重建虚拟机、不丢工作数据。有两条触发路径。

| 路径 | 谁发起 | 适用 |
|---|---|---|
| **控制台下发** | 管理员 | 批量推版本，统一节奏 |
| **VM 管理台自助** | 使用者 | 单台试新版、临时回退 |

两条路径最终走的是同一套执行逻辑。

## 路径一：控制台下发

> 智能体实例 → 版本更新 · 需要 <span class="ap-badge admin">admin</span>

单台或批量选中实例后点「版本更新」：

| 字段 | 约束 |
|---|---|
| 目标版本 | `^[A-Za-z0-9_][A-Za-z0-9_.-]{0,127}$` —— 仅字母数字与 `.` `_` `-`，**不含路径分隔符、空格或 shell 元字符** |

提示语会说清这是异步的：

- 单台：「将为『xxx』下发升级命令，VM 内 agent-manager 会在下次心跳时拉取安装。」
- 批量：「将为选中的 N 个智能体下发同一升级命令（各自下次心跳时执行）。」

::: warning 控制台不校验版本是否存在
后端只校验**格式**，不检查该版本包在仓库里是否真的存在 —— 因为控制面并不去列举镜像仓库。下发一个不存在的版本号，VM 侧会拉取失败。

不确定版本号时，先去某台 VM 的[管理台](/agent-vm/webadmin)看「服务端可拉取版本」列表。
:::

## 路径二：VM 管理台自助

打开 `https://<VM_IP>/manage/`，页面列出三组版本：

| 分组 | 含义 |
|---|---|
| **当前版本** | 正在运行的 |
| **本地已装版本** | 还留在磁盘上的历史版本 —— **能回滚的就是这些** |
| **服务端可拉取版本** | 仓库里有的（FTP 通过 `NLST` 列举；列举失败时降级为空列表） |

选一个版本升级；需要退回时点回滚，留空则退到**上一版本**（一键 undo）。

## 升级时 VM 内做了什么

```
① 拉取 {包名}-{版本}.tar.gz
     协议由平台配置的 AGENT_PKG_BASE_URL 决定（FTP 或 http/https）
② sha256 校验
     镜像地址是明文 http:// 时，摘要是必须的
③ 安全解压到 versions/<版本号>
     防路径穿越
④ 切换 current 符号链接
⑤ restart systemd 单元
⑥ 失败 → 自动回滚到上一版本
⑦ 清理旧版本，保留最新 N 个（AGENT_KEEP_VERSIONS）
```

::: tip 为什么升级很安全
每个版本装在**独立目录**，`current` 只是一个符号链接。

- 升级失败 → 自动把链接切回去，服务几秒内恢复
- 回滚 → 只是改链接指向 + 重启，**不重新下载**，秒级完成
- 工作数据不在版本目录里 → 换版本不影响
:::

## 回滚

回滚**不拉包**，只在已安装的版本之间切换 + 重启服务：

| 指定 | 行为 |
|---|---|
| 填目标版本 | 切到该版本 |
| 留空 | 切回上一版本 |

返回 `409` 的两种情况：没有可回滚的目标；有另一个升级 / 回滚正在进行。

::: warning 太老的版本回不去
旧版本按「保留最新 N 个」清理。清掉之后就不在「本地已装版本」里了，只能重新走升级流程把它拉回来（前提是仓库里还有那个包）。
:::

## 版本包从哪来

包源地址的读取顺序：**数据库里的平台设置优先 → 环境变量 `AGENT_PKG_BASE_URL` 兜底**（密码走加密存储）。

| 协议 | 说明 |
|---|---|
| `ftp://` | 支持 `NLST` 列举可用版本，管理台能显示「服务端可拉取版本」 |
| `https://` | 推荐；摘要校验可选 |
| `http://` | 明文传输，**服务端会强制要求提供 sha256 摘要**才允许升级 |

保留版本数由 `AGENT_KEEP_VERSIONS` 控制。相关变量见[环境变量](/reference/env)。

## 与「重新部署」的区别

| | 版本更新（本页） | 重新部署 |
|---|---|---|
| VM | 复用原 VM | 新建 VM |
| **工作数据** | **保留** | 丢失（除非手工迁移） |
| IP / 凭据 | 不变 | 重新分配 |
| 绑定的密钥 | 不变 | 需重新绑定 |
| 耗时 | 一次心跳 + 安装 | 5–10 分钟 |
| 适用 | agent 版本迭代 | 换模板族、换 OS、实例损坏 |

**日常 agent 版本迭代一律用版本更新**；只有换模板或实例彻底损坏时才重新部署。

## 批量升级的推荐节奏

<ol class="ap-steps">
<li><strong>先确认包在仓库里。</strong> 随便找一台 VM 的管理台看「服务端可拉取版本」。</li>
<li><strong>挑一台非关键实例试。</strong> 单台下发 → 等一次心跳 → 管理台看版本与服务状态。</li>
<li><strong>观察半天到一天。</strong> 看<a href="/observability/request-log">请求日志</a>里这台机器有没有新增错误。</li>
<li><strong>分批推。</strong> 一次 5–10 台，不要一把梭全量。</li>
<li><strong>留好回滚路径。</strong> 确认旧版本还在各机器的「本地已装版本」里再继续下一批。</li>
</ol>

## 常见问题

| 现象 | 处理 |
|---|---|
| 下发后版本没变 | 等下一次心跳；确认 VM 能访问包源；看 VM 内 `journalctl -u agent-manager` |
| 提示版本号非法 | 只允许字母数字与 `.` `_` `-`，不能含路径分隔符或空格 |
| 升级返回 409 | 有另一个升级 / 回滚在跑；或本次升级失败已自动回滚 |
| 升级后 agent 起不来 | 系统会自动回滚；仍异常则手工回滚到上一版本并联系管理员 |
| 想回滚但版本不在列表里 | 已被清理，只能重新升级安装 |
| 包下载失败 | 包源地址不可达，或该版本包不存在；确认内网仓库 |
| `http://` 源升级被拒 | 明文源必须带 `sha256` 摘要，或把仓库换成 https / ftp |
| 管理台看不到「服务端可拉取版本」 | FTP 列举失败会降级为空列表，不影响直接指定版本号升级 |
