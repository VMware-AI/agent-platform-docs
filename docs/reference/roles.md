# 角色与权限矩阵

平台内置三个角色。权限判定发生在**后端 GraphQL 层**，前端路由守卫只是提前拦截，**不是安全边界** —— 绕过前端也拿不到数据。

## 三个角色

| 角色 | 后端枚举 | 中文名 | 定位 |
|---|---|---|---|
| 超级管理员 | `admin` | 超级管理员 | 平台全量读写 |
| 只读用户 | `read_only` | 只读用户 | 观测岗：可看计量与审计，**从不写** |
| 普通用户 | `user` | 普通用户 | 只读自己名下的资源 |

## 权限点

| 权限点 | 覆盖什么 | admin | read_only | user |
|---|---|:---:|:---:|:---:|
| `agent:manage` | 智能体部署 / 启停 / 删除 | ✅ | — | — |
| `key:manage` | 虚拟密钥签发 / 吊销 / 重新生成 | ✅ | — | — |
| `route:manage` | 模型与路由配置 | ✅ | — | — |
| `user:manage` | 用户与角色管理 | ✅ | — | — |
| `audit:view` | 审计日志 / 请求日志 / 请求指标 | ✅ | ✅ | — |
| `metering:view` | 计量中心 / 花费报表 / 预算 | ✅ | ✅ | — |

::: tip 写操作恒为 admin —— 这是构造上的保证
权限矩阵刻意只给 `read_only` 两个 **view** 权限。所有写操作（mutation）按构造只对 `admin` 开放，不依赖任何额外判断。

这意味着「观测岗永远不会误写」不是靠代码里记得加检查，而是靠矩阵本身没有那一项。
:::

## 该给谁什么角色

| 人 | 角色 | 理由 |
|---|---|---|
| 平台运维、部署负责人 | `admin` | 需要接入底座、部署实例、发密钥 |
| 安全 / 合规 / 审计 | `read_only` | 需要看审计轨迹，不应有改配置的能力 |
| 财务 / 成本分析 | `read_only` | 需要看账单与计量，同上 |
| 值班 / NOC | `read_only` | 需要看监控与请求日志 |
| 智能体使用者 | `user` | 只需看自己那台机器；日常操作在 VM 管理台完成 |

::: danger admin 账号要收敛
admin 可以删除资源池、彻底删除实例、吊销全部密钥 —— 任何一项都是全局性破坏。建议：

- 只给必要的少数人
- **每人一个具名账号**，不要共用 `admin@platform.local`
- 靠[审计日志](/observability/audit-log)追踪其操作

给「想看数据的领导」发 admin 是最常见的错误 —— `read_only` 才是那个位置该给的角色。
:::

## 角色变更

在[用户与权限](/console/users)页对某个用户点「更换角色」。变更**立即生效**，用户下次导航时按新角色重新判定。变更本身会记入审计日志（动作：分配角色 / 移除角色）。

::: tip 降权不会踢掉当前会话
用户如果正停在一个现在已无权访问的页面上，页面不会立刻消失，但其中的请求会开始报权限错误，下次导航时被弹回总览。需要立即阻断就直接**禁用账号**。
:::

## 与 VM 内权限的关系

平台角色只管**控制台**。智能体 VM 内部是另一套体系：

| | 平台角色 | VM 内权限 |
|---|---|---|
| 管什么 | 控制台的页面与操作 | VM 的 OS 与自服务管理台 |
| 身份 | 平台用户（邮箱登录） | OS 账户 |
| 授权来源 | 平台 RBAC | Linux 用户 / sudo / htpasswd |

**两者不互通** —— 平台的 `admin` 不会自动获得任何 VM 的 root；VM 使用者也无法从 VM 侧影响平台配置。

::: tip 这是刻意的隔离
使用者能在自己的机器上装工具、改密码、升级 agent，但改不了配额、看不到别人的机器、也关不掉审计。管理员能部署和回收机器、发密钥，但不会自动持有每台 VM 的登录口令（部署时设的密码平台并不存明文）。
:::

## 更细的授权？

v0.0.1 的控制台只有这三个内置角色，粒度到角色为止 —— 界面上没有自定义角色、也没有按资源的细粒度授权。

需要更细的分权时，当前可行的替代方案：

| 需求 | 变通做法 |
|---|---|
| 只让某人管某个部门的机器 | 用不同的**资源池**或**虚拟密钥标签**做逻辑分区，靠流程约束 |
| 只让某人看某类日志 | `read_only` 能看全部四类观测页，无法再细分 |
| 临时授权 | 用完之后把角色改回 `user`，全过程有审计 |

### 后端已有、控制台尚未暴露的能力

平台后端还实现了两套更细的模型，但 v0.0.1 的控制台界面没有对应页面。知道它们存在有助于理解某些字段的来历：

| 能力 | 内容 | 现状 |
|---|---|---|
| **自定义角色 / 权限点** | 可创建角色、给角色配权限点集合、把角色分配给用户 | 后端有，控制台无页面 |
| **部门与成员** | 部门（可带预算上限、可绑定网关）、成员关系（`user` / `dept_admin`） | 后端有，控制台无页面 |

::: tip 这解释了「按部门」维度是哪来的
[计量中心](/observability/metering)的「按部门」维度、以及部署时可选的部门归属，来源就是这套部门模型。v0.0.1 没有部门管理页面，所以这个维度在多数环境里会是空的或只有默认分组 —— 不是坏了。
:::
