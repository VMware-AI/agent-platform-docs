# 实时监控

> 可观测性 → 实时监控 · <span class="ap-badge admin">admin</span> <span class="ap-badge readonly">read_only</span>

按时间窗口聚合网关请求指标，实时刷新关键指标卡片与时序图表。

**这一页回答「现在怎么样」**；历史成本分析去[计量中心](/observability/metering)，逐条追查去[请求日志](/observability/request-log)。

## 时间窗口与刷新

| 控件 | 选项 |
|---|---|
| 时间窗口 | 过去 1 小时 / 6 小时 / 24 小时 / 7 天 / **自定义范围**（开始、结束） |
| 刷新间隔 | 5 秒 / 10 秒 / 30 秒 / 3 分钟 / **关闭** |
| 监控筛选 | 智能体 ID、模型 |

刷新按钮会显示当前间隔（「刷新 (10 秒)」）。

::: tip 刷新间隔怎么选
- **排查进行中的故障** → 5–10 秒
- **挂在大屏上** → 30 秒或 3 分钟
- **只想看一眼历史** → 关闭自动刷新，避免图表一直跳
:::

时间窗口决定后端的聚合粒度：短窗口按**分钟**聚合，长窗口按**小时**或**天**聚合 —— 所以切到 7 天时曲线会变平滑，那是粒度变了，不是流量变稳了。

## KPI 卡片

| 指标 | 说明 |
|---|---|
| 总请求数 | 窗口内的调用总量 |
| 平均延迟 | 平均响应时间 |
| **P95 延迟** | 95 分位响应时间 |
| 输入 Token | prompt tokens |
| 输出 Token | completion tokens |

后端同时算出 **P50 / P95 / P99** 与**错误率**、错误数。

::: tip 看 P95，不要只看平均
平均延迟被大量快请求拉低。P95 才能暴露「一部分人明显卡」的问题。

判断经验：
- P95 ≈ 平均 → 表现均匀，没问题
- P95 是平均的 2–3 倍 → 有长尾，可能是某个上游慢
- P99 远高于 P95 → 少数请求在超时边缘，去请求日志按延迟排序看这批
:::

## 上游健康（各网关）

单独一块展示每个接入网关的健康状况：

| 状态 | 含义 |
|---|---|
| **健康** | 全部上游可达 |
| **部分异常** | 有模型降级或熔断，附「健康 N · 异常 M」计数 |
| **不可达** | 网关本身连不上，显示「网关不可达」 |

后端会给出每个网关下**健康**与**异常**的端点清单，每个端点带模型名与 API Base —— 所以能直接看出是哪个机房的哪个实例挂了，而不用逐个去模型管理里翻。

::: warning 网关不可达时下面的图表也不会更新
指标是从网关侧采的。看到「网关不可达」先解决连通性，别浪费时间分析已经停更的曲线。
:::

## 时序图表

| 图表 | 内容 |
|---|---|
| 请求量 | 窗口内请求数走势 |
| 延迟（平均 / P95） | 双线对比 |
| Token（输入 / 输出） | 双线对比 |
| 请求吞吐量 | Requests/sec |
| 平均响应时间 | ms |
| 活跃智能体数 | 同期在调用的实例数 |
| CPU 使用率 | 资源侧指标 |
| 内存使用率 | 资源侧指标 |

每张图支持 **放大图表**，放大后点「退出放大」返回。窗口内无数据时显示「该时间窗口内暂无数据」。

## 四条典型排查路径

<ol class="ap-steps">
<li><strong>延迟突增</strong> —— 看 P95 曲线的拐点时间 → 到<a href="/observability/request-log">请求日志</a>按该时间窗筛 → 按延迟排序 → 看是哪个模型 / 哪个智能体贡献的。</li>
<li><strong>请求量掉底</strong> —— 先看「上游健康」，网关不可达会让所有调用失败；再看是否有密钥被禁用或超预算（<a href="/console/keys">密钥管理</a>的消费进度）。</li>
<li><strong>错误率上升</strong> —— 到请求日志按状态码分组筛：401 看密钥、429 看限流、5xx 看上游模型健康。</li>
<li><strong>Token 异常上涨</strong> —— 切到<a href="/observability/metering">计量中心</a>按智能体排行，定位到具体实例后查是否有失控的循环调用。</li>
</ol>

## 与 Grafana 的分工

平台内置了一套 Grafana（默认 `http://<EXTERNAL_IP>:3000`，账号 `admin/admin`），预置 LiteLLM 仪表盘与 Prometheus 数据源。

| 用途 | 去哪 |
|---|---|
| 日常巡检、按智能体 / 模型看业务指标 | **本页** |
| 网关内部指标、自定义 PromQL、长周期趋势 | **Grafana** |
| 逐条请求追查 | [请求日志](/observability/request-log) |

::: danger 记得改 Grafana 默认口令
Grafana 默认 `admin/admin` 且**对外暴露在 3000 端口**。生产环境务必在 `.env` 里设置 `GRAFANA_ADMIN_USER` / `GRAFANA_ADMIN_PASSWORD` 后重跑 `./install.sh up`，或干脆用 `BIND_IP` 把它收到内网网卡上。
:::

## 常见问题

| 现象 | 处理 |
|---|---|
| 图表空白 | 该时间窗内确实没有调用；或 prometheus 抓取异常（见 [健康检查](/install/verify)） |
| 「网关不可达」 | 检查网关容器状态与网关地址；见[模型网关接入](/console/gateway-connections) |
| P95 一直很高 | 上游模型本身慢，或有 spec 处于降级状态；看「上游健康」的异常端点清单 |
| 活跃智能体数下降 | 去[智能体实例](/console/agents)看是否有实例转「异常」或「已停止」 |
| 切到 7 天后曲线变平 | 聚合粒度变粗了，属正常现象 |
| CPU / 内存曲线没有数据 | 该指标依赖 prometheus 抓取，确认抓取目标 up |
