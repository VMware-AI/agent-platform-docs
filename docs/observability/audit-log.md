# 审计日志

> 可观测性 → 审计日志 · <span class="ap-badge admin">admin</span> <span class="ap-badge readonly">read_only</span>

记录平台关键操作的审计轨迹：**谁**、在**什么时候**、从**哪个 IP**、对**哪个资源**、做了**什么**、结果**成功还是失败**。

合规检查、安全事件复盘、「这东西是谁删的」都从这一页开始。

## 一条记录包含什么

| 列 | 说明 |
|---|---|
| 操作时间 | 动作发生时刻 |
| 操作者 | 用户名，或「系统」（平台自动任务） |
| 操作类型 | 见下方动作表 |
| 资源类型 / 资源 ID | 被操作的对象，资源 ID 可一键复制 |
| 操作描述 | 人类可读的说明，支持搜索 |
| 结果 | 成功 / 失败 |
| IP 地址 | 操作来源 |
| 详情 | 展开完整记录 |

## 筛选

| 控件 | 选项 |
|---|---|
| 时间范围 | 过去 1 天 / 过去 7 天 / **自定义范围**（起、止） |
| 类别 | 全部类别，或指定资源类别 |
| 操作类型 | 全部，或指定动作 |
| 结果 | 全部 / 成功 / 失败 |
| 列内搜索 | 操作者（ID 或名称）· 资源类型 · 操作描述 |

已应用筛选时有提示，可「清除筛选」。

:::

## 五个实战场景

### 一、排查一次失败的部署

结果筛「失败」+ 类别筛「智能体」+ 时间锁到部署那一刻 → 展开详情看失败原因（vCenter 权限不足、名称冲突、资源不足…）。

### 二、复盘一次误删

类别选被删对象的类型 + 操作类型选「删除」→ 看操作者、时间与 IP。

::: warning 审计能告诉你是谁删的，但恢复不了
删除类操作大多不可逆。这也是为什么资源池、模板、用户的删除都要求**手工输入名称**二次确认。
:::

### 三、季度合规报告

时间范围选整个季度 → 导出 CSV → 按需筛出：密钥签发 / 吊销、用户创建 / 删除、角色变更、资源池接入变更。

### 四、排查异常登录

操作类型选「登录」→ 看 IP 地址分布与失败次数。集中在陌生 IP 的连续失败值得警惕。

### 五、确认「配置到底改没改」

有人说「我没动过啊」的时候，按资源 ID + 操作类型「更新」筛一下，事实自然出来。

## 导出

点 **导出 CSV** 导出当前筛选结果。

| 项 | 值 |
|---|---|
| 单次导出上限 | **5000 条** |
| 内部分批 | 每批 500 条 |
| 超限提示 | 「数据较多，已导出前 N 条」 |
| 无数据提示 | 「当前无数据可导出」 |

::: warning 要全量就分段导
5000 条是硬上限。一个月的数据通常远超这个量 —— 按天或按周切分时间范围，分批导出后再合并。
:::

## 让审计日志真正有用的两件事

<ol class="ap-steps">
<li><strong>每人一个具名 admin 账号。</strong> 大家共用 <code>admin@platform.local</code> 的话，这一页所有记录的操作者都是同一个名字，追责等于零。见<a href="/console/users">用户与权限</a>。</li>
<li><strong>定期导出归档。</strong> 合规要求的留存周期通常长于平台库的实际保留能力，按月导一次存到日志平台最省事。</li>
</ol>

## 与请求日志的区别

| | 审计日志（本页） | [请求日志](/observability/request-log) |
|---|---|---|
| 记录什么 | **人在控制台上做的操作** | **agent 对模型发起的调用** |
| 典型问题 | 谁改了这个配置 | 那次调用为什么 429 |
| 数据量 | 小，随操作次数增长 | 大，随调用量增长 |
| 保留价值 | 合规、安全 | 排障、对账 |

## 常见问题

| 现象 | 处理 |
|---|---|
| 找不到某次操作 | 放宽时间范围；确认类别 / 操作类型筛得不对；用资源 ID 直接搜 |
| 操作者显示「系统」 | 平台自动任务（如周期同步）触发的，不是人工操作 |
| 全是同一个 admin | 大家在共用 bootstrap 账号，给每人建具名账号 |
| 导出条数不全 | 被截断了，缩小时间范围分批导 |
| 想看更早的记录 | 超出平台保留范围时只能从归档的 CSV 里找 —— 所以要定期导出 |
