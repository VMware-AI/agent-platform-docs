# 请求日志

> 可观测性 → 请求日志 · <span class="ap-badge admin">admin</span> <span class="ap-badge readonly">read_only</span>

查看经由网关代理的上游模型请求记录。**逐条级别的事实来源** —— 监控告诉你「有问题」，请求日志告诉你「是哪几条请求出的问题」。

## 一条记录包含什么

| 字段 | 说明 |
|---|---|
| 时间 | 请求发生时刻 |
| 请求 ID | 唯一标识，可一键复制 —— 跨系统追踪时用它 |
| 智能体 / 智能体 ID | 发起方 |
| 用户 | 关联用户 |
| 模型 | 调用的路由 / 模型名 |
| 状态 | HTTP 状态码 |
| 响应时间 | 延迟（ms） |
| 输入 / 输出 Token | 悬停显示「输入 N / 输出 M」 |
| 详情 | 展开单条记录的完整信息 |

## 筛选

| 控件 | 选项 |
|---|---|
| 时间范围 | 过去 1 小时 / 6 小时 / **自定义范围**（起、止） |
| 状态码 | 全部 / 按**状态码分组**（2xx 成功 / 4xx 客户端错误 / 5xx 服务端错误） |
| 列内搜索 | 智能体（UUID 或名称）· 模型名称 · 请求 ID · 用户 ID 或名称 |

已应用筛选时会显示「已应用筛选」提示，可 **清除** 单项或 **清除全部筛选**。

::: tip 先按状态码分组，再收窄时间
排障时的高效顺序是：状态码筛 4xx 或 5xx → 看错误集中在哪个时间段 → 再把时间窗收到那一段 → 最后按模型或智能体定位。反过来先收时间窗容易错过真正的爆发点。
:::

## 状态码对照

| 状态码 | 通常原因 | 去哪修 |
|---|---|---|
| **200** | 正常 | — |
| **401** | 虚拟密钥无效 / 被禁用 / 过期 / 已吊销 / 超出消费上限 | [密钥管理](/console/keys) |
| **403** | 密钥的**作用域**不含该模型或该接口类型 | [密钥管理](/console/keys)的可调用模型 / 可调用接口 |
| **404** | 请求的模型名不存在 —— 多半写成了上游模型原名而不是**路由名** | [网关路由](/console/routes) |
| **429** | 触发 RPM / TPM / 最大并发限制 | 调高限额或分散流量 |
| **500 / 502 / 503** | 上游模型服务异常 | [模型管理](/console/models)看健康状态 |
| **504** | 上游超时 | 上游负载或网络；看[实时监控](/observability/monitor)的 P95 |

## 导出

点 **导出 CSV** 导出当前筛选结果。导出中会显示「导出中…」，数据量大时会截断并提示「数据较多，已导出前 N 条」。

::: warning 大范围导出会被截断
需要完整数据时，把时间范围切成小段分批导出，而不是一次拉一个月。
:::

## 四个实战用法

### 一、用户报「我的 agent 报错了」

<ol class="ap-steps">
<li>时间范围选事发前后 1 小时。</li>
<li>状态码筛 4xx / 5xx。</li>
<li>智能体列搜该用户的实例名或 ID。</li>
<li>展开「详情」看具体错误，对照上方状态码表处理。</li>
</ol>

### 二、找最慢的请求

按响应时间排序取 Top N，然后找共同点：同一个模型？同一个时间段？同一台智能体？同一类超长 prompt？

### 三、对账

某个智能体的账单对不上时，用智能体 ID 筛出全部记录并导出 CSV，与[计量中心](/observability/metering)的汇总比对。差异通常出在：时区边界、已回收实例的归属、或缓存 token 的计费口径。

### 四、追一条具体请求

用户能提供请求 ID 时，直接在请求 ID 列搜索 —— 这是最快的路径，一步到位。

## 数据是怎么进来的

```
litellm 网关 ──OTLP──▶ otel-collector ──写 jsonl──▶ backend 摄入 worker ──▶ PostgreSQL
                        (127.0.0.1:4317/4318)      (共享文件 tail)
```

`otel-collector` 是 v0.0.1 引入的采集环节，相关调优项（批大小、超时、文件滚动）见[环境变量](/reference/env)的 OTel 一节。摄入模式由 `REQUESTLOG_INGEST_MODE` 控制（`warn` / `fail` / `off`）。

::: warning 请求日志一直为空
按顺序检查：

1. 智能体是否真的通过网关调用了模型 —— 看[实时监控](/observability/monitor)的请求量
2. `docker compose -p agent-platform ps` 里 `otel-collector` 是否 running
3. `docker compose -p agent-platform logs backend | grep -i requestlog` 有没有摄入报错
:::

## 与审计日志的区别

| | 请求日志（本页） | [审计日志](/observability/audit-log) |
|---|---|---|
| 记录什么 | **agent 对模型发起的调用** | **人在控制台上做的操作** |
| 典型问题 | 那次调用为什么 429 | 谁改了这个配置 |
| 数据量 | 大，随调用量增长 | 小，随操作次数增长 |
| 保留价值 | 排障、对账 | 合规、安全 |

## 常见问题

| 现象 | 处理 |
|---|---|
| 列表为空 | 见上方「请求日志一直为空」 |
| 只有部分调用有记录 | 采集有丢失，看 otel-collector 的批处理与文件滚动配置 |
| 智能体列显示 ID 而非名称 | 该实例已被彻底删除，只剩 ID |
| 导出的 CSV 条数不全 | 被截断了，缩小时间范围分批导 |
| 想看请求体 / 响应体 | 列表记录的是调用元数据（模型、Token、延迟、状态码）加一个可选的 `detail` 字段，展开「详情」看到的就是它；完整的 prompt / completion 正文不在这一页 |
